# /lhg-fullstack:ship —— 发布门禁

用户输入在 `$ARGUMENTS` 中：`[项目目录]`（缺省当前目录）。这是上线前的最后一道门，结论只有"放行"或"拦截"，没有"大概行"。

## 门禁检查（按序执行，一票否决）

### 门 1：审计清零
跑 `/lhg-fullstack:audit` 全流程。blocker 必须为 0；warning 必须全部处理（修复或有豁免理由+有效期）。不满足 → **拦截**。

### 门 2：测试
1. 运行项目测试命令（如 `pnpm test`）；无测试命令时，核心链路必须有手工走查记录。
2. 新增生产代码有对应测试，或在报告中写清豁免理由。**TDD 硬门**：无测试的生产代码不许放行（插件 hook 会在 commit 前拦截，此处复核）。

### 门 3：上线清单
- [ ] 环境变量：生产环境已配置，`.env` 未提交，`.env.example` 已更新
- [ ] 数据库：migration 已在类生产环境跑过，RLS 已开
- [ ] 密钥：无硬编码密钥（脚本已查），第三方 key 已换成生产 key
- [ ] 构建：`pnpm build` 通过，无报错无新增 warning
- [ ] 回滚：知道出问题怎么回滚（上一个可用版本/数据库备份）

### 门 4：内容终审
- [ ] 页面无编造的数字、评价、客户 logo、价格
- [ ] 错误页/空状态/加载态齐备
- [ ] 移动端核心流程走查一遍

## 输出
```markdown
# 放行 / 拦截：<项目名>（日期）
- 门 1 审计：通过（blocker 0 / warning n 已处理）
- 门 2 测试：通过（xx 用例）/ 豁免（理由）
- 门 3 上线清单：x/y 通过
- 门 4 内容终审：通过
- 结论：放行 / 拦截（拦截必须写清哪扇门、为什么、怎么修）
```

拦截时不许说"修完再来"，要给出**具体的修复步骤**。
