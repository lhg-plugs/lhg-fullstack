# lhg-fs-audit：前后端自查流程

> 目标：把"自我检查"变成固定流程，而不是凭感觉扫一眼。
> 核心纪律：**先跑脚本（机器），再做评审（人）；blocker 不清零，不许说做完了。**

## 1. 何时使用

- 完成功能开发后、提交前 → 跑全流程
- 上线/发布前 → 跑全流程 + 第 6 节上线检查
- 只想快速看一眼 → 只跑第 2 步（脚本），5 秒出结果

## 2. 第一步：跑确定性审计脚本（必做，零 LLM 成本）

在项目根目录执行插件自带的两个脚本（用你所在平台执行本地脚本的方式）：

```
python3 <插件目录>/scripts/audit/frontend_audit.py --target <项目目录>
python3 <插件目录>/scripts/audit/backend_audit.py  --target <项目目录>
```

- 脚本输出 JSON（含每条发现的文件、行号、规则说明）与人类可读报告。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`（有 blocker 即非零退出，供 hook/CI 用）；想要更严的门禁可设为 `warning`。
- 脚本自动跳过 `node_modules/.next/dist/build/.git` 等目录；单体仓库可对子目录单独跑。
- 脚本只做"机器可判定"的事：模板相、硬编码、密钥、SQL 拼接、空 catch 等。它判定不了品味和业务逻辑，那是第 4 步的事。

## 3. 第二步：分级

所有发现按三级处理，定义如下：

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 上线后会出事：密钥泄露、SQL 注入、无 RLS、编造数据、移动端横滚 | 必须修，不修不许提交（commit 前的 hook 会拦截） |
| warning | 大概率是坑：无分页、错误形状不统一、缺输入校验、可点击 div | 本次迭代修掉；修不掉要写理由进报告 |
| nit | 洁癖项：命名不一致、魔法数字、注释掉的代码 | 顺手修，不顺手就记下来 |

分级是死的，判断是活的：如果某条 warning 在你的场景里就是会出事，把它升成 blocker，并在报告里写清理由。

## 4. 第三步：自动修复 blocker

1. blocker 逐条修，修一条跑一遍对应脚本确认消失。
2. 修的时候遵守"最小改动"：只修问题本身，不要顺手重构。
3. 修不掉的 blocker（如需用户提供真实文案/密钥）：列进报告的"需人工处理"区，**不许**为了清零而删规则或改脚本阈值。

### 修复顺序（blocker 不止一个时）

1. **安全类先修**：密钥泄露、SQL 注入、无条件删除——这些是"正在流血"的。
2. **其次数据类**：无 RLS、返回密码哈希、错误吞没。
3. **再修诚实类**：编造文案、lorem ipsum、TODO 残留。
4. **最后结构类**：移动端横向滚动、固定大宽度、缺 alt。

同一文件的多个 blocker 一次改完，跑一次脚本确认，不要修一条跑一次浪费时间。

## 5. 第四步：人工评审（脚本覆盖不到的）

### 前端评审清单
- [ ] 文案全部真实：数字、评价、客户、价格，无一编造（对照 PRODUCT.md）
- [ ] 视觉：没有模板相（对照 lhg-fs-frontend 第 3 节），页面之间风格一致
- [ ] 对比度：正文抽查 3 处，达到 AA
- [ ] 动效：时长合理，有 reduced-motion 支持
- [ ] 空状态/错误状态/加载状态：三个状态都有设计，不是只有"有数据"一种样子

### 后端评审清单
- [ ] 鉴权：每个接口的鉴权要求与契约卡片一致，无"默认公开"
- [ ] 越权：RLS 策略有测试证明 A 看不到 B 的数据
- [ ] 错误码：与契约卡片一致，无新增的裸字符串错误
- [ ] 幂等：创建类接口实测重复请求不重复创建
- [ ] 边界：空列表、超大 limit、非法参数，三个 case 都试过

### 评审输出
每项写"通过 / 不通过（原因）"，不通过的进待办，不许写"大概没问题"。

## 6. 第五步：输出报告

报告模板：

```markdown
# 自查报告：<范围>（日期）
## 结论：通过 / 不通过
## blocker（n）：已修 n，剩余 n
- [规则ID] 文件:行 —— 说明 —— 状态（已修/需人工）
## warning（n）：已修 n，豁免 n（理由）
## nit（n）
## 人工评审：前端 x/y 通过，后端 x/y 通过
## 需人工处理
- ...
```

报告存进项目（如 `docs/audit-YYYYMMDD.md`），下次回归时对照。

## 7. 豁免规则

- 豁免只针对 warning/nit，blocker 不许豁免。
- 豁免必须写理由 + 有效期（如"演示版，正式上线前补"），到期复查。
- 豁免清单进报告，藏着不写等于没豁免。

## 8. 反模式

- ❌ 只跑脚本不做人工评审——脚本抓不到"文案是编的"这种问题
- ❌ 为了清零改脚本规则——这是作弊，不是自查
- ❌ "warning 太多了，先上线再说"——warning 就是未来的 blocker
- ❌ 自查报告只写"通过"两个字——没有过程的结论不可信

## 9. 误报处理

规则是启发式，一定会误伤。误报不可怕，乱处理才可怕：

1. **判断三问**：这行代码真的有问题吗？这条规则的本意是什么？按规则改了会不会破坏功能？
2. **确认误报**：在代码处加一行注释说明原因（如 `// 演示用占位图，上线前替换 -- 豁免 FE-HON-004`），并记入报告的豁免清单。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现代码提 issue（见第 11 节），说明"期望行为"，不要自己改脚本阈值。

## 10. 审计频率与回归

- **每次完成功能**：只跑脚本（5 秒），blocker 当场修。
- **每次提交**：hook 自动跑，有 blocker 会被拦截。
- **上线前**：跑本 skill 全流程（含人工评审）。
- **修完回归**：只跑对应的单个脚本确认消失，不用每次全量。
- **每周**：抽 3 个 warning 看看有没有正在变成 blocker 的趋势（如"无分页"的接口数据量涨了）。

## 11. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是"我觉得没问题"）？→ 没跑不算做。
2. blocker 是否清零或全部列入"需人工处理"？→ 有遗漏就补。
3. 人工评审清单是否逐项打勾？→ 打勾要有依据。

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，确认坏 fixture 的 blocker 全命中、好 fixture 零 blocker（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-fullstack/issues，正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现代码。
