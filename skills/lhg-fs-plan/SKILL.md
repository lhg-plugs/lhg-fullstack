# lhg-fs-plan：需求澄清与架构规划

> 目标：把小白的一句话想法，变成一份"可执行、可验收"的开发计划。
> 核心纪律：**没有澄清的需求不写代码，没有拆分的任务不开工。**

## 1. 何时使用

- 用户说"做个 XX 系统/网站/应用"，需求只有一两句话时 → 必须先跑本 skill
- 在已有项目上加一个中等以上规模的新功能时 → 跑本 skill 的精简版（只做第 1、4 步）
- 需求已经非常明确（有原型图、有字段清单）时 → 可跳过第 1 步，直接做 2-4 步

## 2. 输入与输出

- **输入**：用户的一句话需求（可能很模糊，这是正常的）
- **输出**：一份 `PLAN.md`，包含：澄清结论、架构决策、任务清单、验收标准

## 3. 第一步：需求澄清（最多 5 个问题）

### 3.1 提问原则

1. **一次只问最关键的**：按"目标用户 → 核心场景 → 数据 → 约束 → 非目标"的顺序问，问完即停，不要为了凑数而问。
2. **先开放，后收敛**：先问开放式问题理解意图，再用选择题帮用户做决定（给 2-4 个选项 + "其他"）。
3. **不替用户做决定**：涉及产品方向、取舍的问题必须问，不许脑补。
4. **每个问题都要有目的**：问之前先想清楚"这个答案会改变什么技术决策"，答不上来的问题不问。

### 3.2 必问清单（按需取用，不超过 5 个）

1. **谁用？**——"这个应用是给谁用的？（比如：我自己用 / 给客户演示 / 给真实用户用）"
   → 决定质量档位与数据真实性要求。
2. **核心场景？**——"用户打开它之后，最核心的 1-3 个操作是什么？"
   → 决定 MVP 范围，其他一律进二期。
3. **数据从哪来？**——"数据是用户自己录入，还是接第三方，还是先用示例数据？"
   → 决定是否需要数据库设计与后台管理。
4. **有什么不能做？**——"有没有明确不做的功能，或者必须避开的坑？"
   → 划定边界，防止范围蔓延。
5. **上线形态？**——"跑在自己电脑演示就行，还是要部署到公网给别人访问？"
   → 决定是否需要鉴权、部署、安全基线。

### 3.3 停止条件

- 5 个问题问完，或用户说"就这样，开始吧"，或信息已足够做架构决策 → 进入第二步。
- 用户中途改需求 → 回到本步重新澄清，不要带着旧计划硬走。

## 4. 第二步：架构决策

### 4.1 默认技术栈

除非有明确理由偏离，否则直接采用默认栈，不要在选型上反复横跳：

- **前端**：Next.js（App Router）+ Tailwind CSS
- **后端**：Next.js API Routes（轻量场景）或独立后端（复杂场景见 4.2）
- **数据库**：Supabase Postgres（含 Auth、RLS、Storage 一套）
- **部署**：Vercel（前后端一体）

一套 TypeScript 通吃前后端，小白的心智负担最低。

### 4.2 偏离默认栈的判断条件

| 信号 | 偏离方向 |
|---|---|
| 需要定时任务、长连接、复杂后台 job | 后端独立（FastAPI / NestJS），前端仍 Next.js |
| 已有明确的移动端需求 | 先做响应式 Web，移动端二期再议，不要一期双端并行 |
| 纯展示、无交互、无数据 | 降级为静态站点，不要上数据库 |
| 用户点名了某个技术栈 | 听用户的，但把 trade-off 讲清楚 |

### 4.3 架构决策记录（ADR 轻量版）

每个重要决策写一行进 `PLAN.md`，格式：

`- [决策] 选用 Supabase 而非自建 Postgres —— 理由：免运维、自带 Auth/RLS；代价：供应商锁定（可接受，MVP 阶段）`

## 5. 第三步：任务拆分

### 5.1 拆分规则

1. **粒度 2-5 分钟**：每个任务是一个"可独立验证"的小步骤，例如"创建 users 表迁移"而不是"做用户系统"。
2. **先骨架，后血肉**：先搭通"页面→接口→数据库"的最小链路，再逐个丰富功能。
3. **标注并行点**：前端页面与后端接口只要契约（API 形状）先定好，就可以并行开发。在任务清单里明确标出"可与 Nx 并行"。
4. **依赖排序**：数据库 schema → API 契约 → 前后端实现 → 联调 → 自查。

### 5.2 任务清单格式

```markdown
## 任务清单
- [ ] T1 建库：Supabase 建表 users / orders（含 RLS 策略）——验收：SQL 可执行
- [ ] T2 API：POST /v1/orders 创建订单（含幂等键）——验收：curl 返回 201 且 code/message 形状正确
- [ ] T3 前端：订单列表页（移动端优先）——可与 T2 并行 ——验收：390px 无横向滚动
```

## 6. 第四步：验收标准

每个任务必须有"可验证"的完成定义，拒绝"我觉得差不多了"：

- **功能验收**：具体的操作路径 + 预期结果（写进任务清单的"验收"栏）。
- **质量验收**：确定性审计脚本零 blocker（见 lhg-fs-audit）；新增生产代码有对应测试或明确豁免理由。
- **诚实验收**：页面上没有编造的文案、数据、用户评价（见 lhg-fs-frontend 的内容诚实规则）。

## 8. 反模式（不要这么做）

- ❌ 跳过澄清直接写代码——返工成本是澄清成本的 10 倍以上
- ❌ 一次性问 10 个问题——用户会烦，答案质量也会下降
- ❌ 任务粒度是"做用户系统"这种周级任务——无法验证、无法并行
- ❌ 验收标准写"跑起来就行"——等于没有标准

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 是否问了超过 5 个问题？→ 下次合并同类问题。
2. 任务粒度是否有超过 15 分钟的？→ 拆得不够细。
3. 是否有任务没有可验证的验收标准？→ 补上。
4. 是否替用户脑补了产品决策？→ 下次必须问。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用"做个小区团购接龙小程序"走一遍本 skill，检查是否能在 5 问内收敛、任务是否可并行、验收是否可验证。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-fullstack/issues。
