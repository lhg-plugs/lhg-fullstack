# lhg-fs-memory：项目记忆规范

> 目标：让 AI 在多次会话之间"记得"项目，不用每次从头讲一遍。
> 核心纪律：**事实与决策分离；变更发生时同步更新记忆，而不是"有空再补"。**

## 1. 何时使用

- 新项目启动（lhg-fs-plan 之后）→ 创建三件套
- 新会话接手老项目 → 先读三件套，再动手
- 需求/架构/设计发生变更 → 同步更新对应文件

## 2. 三件套

放在项目根目录（或 `docs/` 下），三个文件各管一摊：

### PRODUCT.md —— 产品事实

写"产品是什么"，不写"怎么做"：

```markdown
# PRODUCT：<产品名>
## 一句话介绍
## 目标用户
## 核心场景（≤5）
## 非目标（二期/不做）
## 关键产品事实
- 定价：待定（不要编数字）
- 上线形态：公网 / 内测
## 术语表
- <业务术语>：<一句话解释>
```

### APP.md —— 技术事实

写"工程是什么"，给接手的人看：

```markdown
# APP：<产品名>
## 技术栈
- 前端 / 后端 / 数据库 / 部署
## 目录结构
- app/：页面路由；components/：组件；lib/：工具…
## 常用命令
- pnpm dev / pnpm build / pnpm test
## 环境变量
- 必填：DATABASE_URL, SUPABASE_ANON_KEY…
## 外部依赖
- Supabase 项目链接、第三方 API…
```

### DESIGN.md —— 设计事实

写"长什么样"，给前端看：

```markdown
# DESIGN：<产品名>
## 设计令牌
- 主色：#1a56db（--color-primary）
- 字体：Inter / 系统栈；字阶 12/14/16/20/24/32
- 圆角：8px 卡片 / 999px 胶囊；间距基数 4px
## 风格关键词
- 如：克制、留白多、圆角小、浅色为主
## 页面清单
- /：落地页（hero 左文案右图）
- /dashboard：数据看板…
## 不许出现的（模板相黑名单）
- 紫粉渐变、霓虹暗黑…
```

## 3. 写作规范

1. **事实 vs 决策分离**：PRODUCT 写"是什么"（事实），决策过程（"为什么选 Supabase"）进 PLAN.md 的 ADR，不混在一起。
2. **短**：每个文件不超过 100 行，写不下说明该拆了。记忆是索引，不是文档库。
3. **诚实**：不知道的写"待补充"，不许编。编进记忆的假事实会污染之后所有会话。
4. **及时**：需求变更改 PRODUCT，换栈改 APP，改风格改 DESIGN。改代码的同时改记忆，不要攒。
5. **写日期**：三件套头部写最后更新日期；超过 30 天没更新的，下次审查时标黄提醒。

## 4. 新会话加载顺序

1. 先读 PRODUCT.md（知道在做什么）
2. 再读 APP.md（知道怎么跑起来）
3. 做前端时读 DESIGN.md（知道长什么样）
4. 然后才看代码、动手

如果三件套缺失或明显过时，先问用户"记忆好像过期了，要不要我按现状重建"，不要闷头按过期记忆干活。

## 5. 反模式

- ❌ 把三件套写成几千字需求文档——没人读，包括 AI（上下文很贵）
- ❌ 记忆里写"计划做"——记忆只记录"已确定"的，计划进 PLAN.md
- ❌ 换了技术栈不改 APP.md——下个会话会按旧栈生成代码
- ❌ 在记忆里记密钥——记忆文件进仓库，密钥进环境变量，绝不混放

## 6. 记忆腐烂与定期审查

记忆会过期，过期记忆比没记忆更害人：

1. **症状**：记忆里写的目录结构跟代码对不上；新人（或新会话）按记忆踩了已知坑。
2. **审查**：每月花 10 分钟过一遍三件套——删掉过期的、补上新增的、把"待补充"清掉或注明为什么还补不上。
3. **责任**：谁最后改相关代码，谁顺手改记忆。不要攒到"有空再补"。

## 7. 多项目与单体仓库

- **单体仓库**：根目录放总体 `PRODUCT.md`（产品级事实），每个子应用/包目录下放自己的 `APP.md` / `DESIGN.md`。
- **多仓库**：每个仓库独立三件套；组织级另放一份架构总览（系统间关系、共用服务），不塞进单个仓库的记忆。
- **个人实验项目**：三件套可以压缩到一个 `MEMORY.md`，但事实与决策分离的原则不变。

## 8. 与 CLAUDE.md 的分工

两者都给 AI 看，但管的事不同，不要重复：

| 文件 | 管什么 | 举例 |
|---|---|---|
| CLAUDE.md | 工作指令：怎么干活、禁什么 | "提交前跑测试""不用 emoji" |
| PRODUCT.md | 产品事实：做什么、给谁做 | 目标用户、核心场景 |
| APP.md | 技术事实：栈、目录、命令 | pnpm dev、环境变量 |
| DESIGN.md | 设计事实：长什么样 | 设计令牌、页面清单 |

判断方法：这句话是"要求 AI 怎么做"→ CLAUDE.md；是"项目是什么样"→ 三件套。

## 9. 自检与反馈

每次更新记忆后自检：

1. 三个文件是否各不超过 100 行？→ 超了就拆或删。
2. 是否有"待补充"超过两周没补？→ 追问用户。
3. 是否有编造的事实混进去？→ 删掉或标待补充。

标准冒烟用例：删掉记忆后开新会话，只给三件套，看 AI 能否不问重复问题直接开工。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-fullstack/issues。
